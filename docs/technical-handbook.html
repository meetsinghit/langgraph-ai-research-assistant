System architecture

A single-user, local-first web application with a clear separation between UX, control plane, research engine, external services, and durable state.

Figure 01 / logical architectureFive core layers + security

Control plane

FastAPI authenticates, validates and persists new runs. A bounded manager owns worker lifecycle, SSE event distribution, cancellation, and capability-gated recovery. Request settings are frozen at run creation.

Execution plane

LangGraph coordinates research nodes. Gemini supplies planning, tool decisions, synthesis, and review. Tool adapters enforce search/fetch authorization, deadlines, source integrity and output-size limits.

LangGraph internals

Understand the agent graph as a controlled state machine: channels, reducers, routing decisions, bounded retries, and typed outcomes.

Durable graph state

What persists

Question, plan, findings, source records, review status, iteration counters, depth/evidence settings and structured fields needed by the graph. Checkpoints use explicitly serializable data.

STATE / CHECKPOINT
Runtime-only context

What never belongs in state

Live RunDeadline, cancellation handle, progress sink, injected clock and per-run query cache. These travel via LangGraph runtime context and are reconstructed on resume.

RUNTIME CONTEXT
Figure 03 / conditional workflow topologyOne graph, guarded branches

State and reducers — the core abstraction

Nodes are functions of state. Each node returns a partial update; reducers specify how the update is merged. A reducer such as operator.add accumulates a list, whereas an unannotated channel is generally overwritten by its next update. The real application's schema is richer than the pedagogical example below.

  Illustrative LangGraph mini-pattern · not a copy of the repo
from typing import Annotated, Literal
from typing_extensions import TypedDict
import operator
from langgraph.graph import StateGraph, START, END

class ResearchState(TypedDict):
    question: str
    notes: Annotated[list[str], operator.add]
    enough_evidence: bool

def gather(s: ResearchState) -> dict:
    return {"notes": [f"Investigate: {s['question']}"],
            "enough_evidence": True}

def write(s: ResearchState) -> dict:
    return {"notes": ["Draft answer from gathered evidence"]}

def route(s: ResearchState) -> Literal["write", "__end__"]:
    return "write" if s["enough_evidence"] else END

b = StateGraph(ResearchState)
b.add_node("gather", gather)
b.add_node("write", write)
b.add_edge(START, "gather")
b.add_conditional_edges("gather", route, {"write": "write", END: END})
b.add_edge("write", END)
app = b.compile()
print(app.invoke({"question": "What is a reducer?", "notes": [],
                  "enough_evidence": False}))

Why not just a linear script?

Dynamic routing

The reviewer can route back to evidence acquisition when an answer is superficial or citations are inadequate—within caps.

Durable steps

Checkpoint boundaries allow conservative crash recovery. Resume can re-execute the interrupted node: at-least-once, not exactly-once.

Inspectable lifecycle

Each node and tool produces typed status events so UI, operations, and benchmark harness can observe the run.

Important distinction LangGraph's END constant represents the terminal node ("__end__"); it is not a normal business node. State channels, reducer behavior and routing annotations must be deliberately designed to avoid accidental parallel paths.
CHAPTER 05 / ENGINEERING REFERENCE

Evidence, citations & research depth

The trust model of the research product: a source can be discovered without being fetched, and fetched without being factually correct.

DISCOVERED

Search result

Title, URL and snippet supplied by a search backend. Useful for navigating toward evidence; page content has not been retrieved or independently validated.

RETRIEVED

Fetched evidence

Allowed webpage fetched with HTTP controls, processed, and linked to a canonical source ID. Retrieval demonstrates provenance, not ultimate truth.

INCOMPLETE

Insufficient support

Requested topics, citations, or required retrieved evidence are missing. The product returns a visibly qualified result rather than silently inventing proof.

Canonical source identifiers

The engine assigns source references such as [S1], [S2] in deterministic order, preserves the strongest available provenance for a URL, and uses those IDs consistently in answers and the browser Source Inspector. IDs are scoped to each run—not the entire conversation.

Evidence policyWhat citations can supportFailure behaviorWhen to use
Balanced defaultRetrieved evidence preferred; discovered-only citations allowed with explicit snippet limitationQuality warnings when support is thinFast learning, exploratory research
VerifiedFactual citation support must come from successfully retrieved pagesIncomplete result if thresholds or eligibility cannot be metDocumentation-grounded technical learning and important research

Adaptive depth — interactive policy explainer

Quick Research

Lower query/retrieval budget, short answer, essential citations, speed-first. Uses real backend DepthPolicy; not just a word-count prompt.

Two independent axes Research depth controls investigation effort and synthesis detail. Evidence policy controls what may support a citation. A long answer can still have weak evidence; a short answer can be complete.

Evidence shaping and bounded context

The original live POC once sent nearly 190k prompt characters after a huge webpage. Phase 4A constrained model-visible tool result messages to around 8,000 characters and synthesis evidence to around 6,000 characters by default. Later depth policies permit explicit bounded variation. Sentence-focused selection keeps salient, query-relevant passages instead of forwarding full webpage dumps.

Unverified snippets remain a visible caveat The live 3.8 Flash answer explicitly marked several claims as unverified snippet. That behavior is intentional under Balanced mode. For stronger documentation grounding, use Verified; expect additional retrieval effort and possible incomplete outcomes.

Gemini model and thinking control

A backend-validated model registry lets each research run freeze its model, reasoning setting, depth and evidence policy.

One key, multiple eligible models

The same configured Gemini API credential is reused for allowed model IDs. The registry separates documented free-tier eligibility from actual availability for a particular project and prohibits silent paid fallbacks.

SERVER-SIDE ALLOWLIST

Immutable per-run snapshot

Model ID, thinking level, depth and evidence mode are validated on the API, saved in SQLite, used consistently by worker/LLM calls, and restored for history or resume. Concurrent runs do not mutate a global model instance.

Event-driven progress

Run lifecycle events are committed to SQLite with monotonically increasing sequence IDs before broadcast. A fetch-based SSE consumer can include Bearer authentication, reconnect with Last-Event-ID, replay persisted events, deduplicate by sequence and resume its progress view without creating another run.

  Illustrative SSE envelope
id: 17
event: tool.finished
data: {"seq":17,"type":"tool.finished",
       "payload":{"tool":"fetch_page","ok":true,
                  "latency_ms":812,"host":"docs.langchain.com"}}

# Content-free event payloads: no retrieved page text or provider secrets.

Idempotency

Repeated POST using the same key and settings returns the same run, not duplicate work. A changed configuration with the same key yields an explicit conflict.

Replay safety

Historical event replay is coordinated with live tailing to avoid a subscribe/replay gap. Client sequence dedup prevents duplicate presentation.

Static production UI

FastAPI serves the built React assets on the same origin. The API stays protected; frontend bundles are public but contain no credentials.

Threat boundary Browser stores the local app Bearer token in memory by default, not in a URL or frontend bundle. A page refresh may require reconnecting. Local loopback access is not equivalent to hardened public authentication.

SQLite, checkpoints & crash recovery

Sessions persist between restarts; interrupted work can be resumed cautiously; read history is separate from executing a new run.

app.db · user-facing data

Application tables

sessions · runs · run_sources · run_events. Contain session titles, immutable run settings, final answer, sources, status, metadata, sequenced events and content-free diagnostics.

checkpoints.db · execution-only data

LangGraph checkpoints

SqliteSaver persists graph state at node boundaries and allows conservative recovery of interrupted runs. Checkpoints are pruned for terminal runs under the documented policy.

Why each follow-up is a new LangGraph run

Reusing the prior research thread's findings could accidentally satisfy minimum-evidence gates before new pages are fetched. Instead, a follow-up gets a new run and fresh budgets, with bounded, server-derived prior conversation context marked as context only—not citable evidence. The surrounding session remains the same for the user.

At-least-once semantics A tool action in the interrupted node can repeat after recovery. This may be acceptable for read-only research, but would not be sufficient for payments or other irreversible actions without external idempotency.
Checkpoint deletion ≠ secure erasure SQLite/WAL pages and SSD behavior can retain remnants after logical pruning. Treat checkpoint files and backups as sensitive, secure the local disk and use appropriate key/disk protection.
CHAPTER 09 / ENGINEERING REFERENCE

Security threat model & trust boundaries

Untrusted webpages may inform an answer; they may not change policy, request secrets or expand tool capabilities.

“External information is evidence—not authority.”
The principal design rule behind Phase 4C.

The lethal trifecta—and how the design breaks it

1

Private data

Provider secrets, local environment, internal runtime policy and user session content.

2

Untrusted input

Search snippets, fetched pages, metadata, hidden HTML, error text and malicious instructions.

3

Outbound channel

Tool-supplied search queries or URL fetches could become exfiltration channels if unconstrained.

Deterministic boundary fetch_page is allowed only for URLs legitimately registered by web_search during the same run; tool names/arguments are allow-listed; DLP refuses credential-shaped arguments. This reduces unauthorized exfiltration even if an LLM follows hostile webpage instructions.

What the 25 adversarial cases actually prove

Twenty deterministic-control cases and five explicitly labeled scripted model-behavior cases were reported. Together they test known injection, exfiltration and authorization scenarios offline. They do not establish universal immunity to live prompt injection or a zero-percent attack-success rate.

Reliability, limits & observability

The engine is not designed to “always succeed.” It is designed to fail legibly, within explicit budgets, and without concealing unknown measurements.

Error taxonomy and response

CategoryTypical causeExpected behavior
provider_transientGemini HTTP 5xx / temporary service failureBounded retry, safe user-facing explanation
rate_limitQuota 429 / Retry-AfterBounded, deadline-aware retry or safe failure
model_accessDenied/unavailable model 401/403/404 as classifiedPermanent failure; no alternate-model fallback
validationInvalid tool or run settingsReject before execution
empty_resultsSearch returned nothingControlled broadening without invented terms
policy / dlpUnauthorized URL/tool or secret-shaped valueRefusal; no raw sensitive arguments echoed
timed_out / cancelledDeadline reached / user cancellationControlled terminal outcome at safe boundary
incompleteInsufficient topic/evidence supportQualified saved answer; not falsely approved

180s default total budget

Global cooperative execution deadline covers workflow nodes, retries and tool actions. In-flight blocking calls may overrun until they return.

Bounded provider retries

Transient classes retry with capped backoff/jitter and any safe Retry-After behavior; permanent errors do not multiply attempts.

Per-run search cache

Successful identical queries are deduplicated using conservative whitespace/case normalization; failed queries and webpage fetches are not cached.

Token accounting: observed, estimated, unavailable

Earlier metrics incorrectly showed zero usage for structured-output plan/review calls. The updated provider integration captures usage when available, records source/coverage and never conflates missing tokens with zero. After crash/resume, the usage scope may be since_resume, because lost provider metadata from the crashed segment cannot be reconstructed.

What was observed

3.8 Flash took about 2.4× as long and produced ~59% more output tokens. It also fetched one additional official page. Thinking-token data was available for 3.8.

What cannot be concluded

These are not controlled model benchmarks: thinking effort, external search latencies, evidence retrieved and stochasticity differ. “More tokens” does not establish higher accuracy.

Earlier functional acceptance

The first live SecOps browser run completed in 16.8 seconds, with 6,292 input / 558 output tokens, one research iteration and a persisted, review-approved answer. History survived a full stop/start without rerunning Gemini. These results confirm the local user journey but not general reliability under production load.

Recommended benchmark protocol Compare candidate models on the same fixed question set and evidence policy, with matched thinking levels where supported, multiple repetitions, source-quality rubric, latency distribution and token/cost reporting. Do not select a “winner” on a single run.

Explain it in a technical interview

Turn the implementation into a crisp problem/architecture/controls/results narrative instead of listing libraries.

60-second project pitch

I built a local-first, full-stack AI Research Assistant with LangGraph and Gemini. It plans research, searches and retrieves web evidence, generates citation-grounded answers, then checks source support and topic completeness before finishing. I exposed it through FastAPI and a React UI with streaming progress, SQLite history and checkpoint recovery. The key engineering choices were deterministic tool authorization, provenance-aware citations, bounded retries/deadlines, and offline quality/security evaluation. It now supports per-run model, thinking, depth and verification policies, and I validated the end-to-end flow live with two Gemini models.

Business framing

Positions the app as research productivity tooling: better source transparency, lower manual context switching, reusable evidence, faster learning and auditable output quality. Do not invent ROI percentages without a measured baseline.

Technical framing

Emphasize state invariants, runtime-vs-durable context, at-least-once recovery, prompt-injection boundary, provider error taxonomy and testability across offline and live environments.

Questions you should be ready to answer

Why LangGraph rather than a normal Python loop?
Explicit state channels/reducers, conditional review routing, checkpoint boundaries and node-level observability make branching and recovery tractable. It costs more architecture effort than a fixed script; that is justified when the workflow is iterative and auditable.
Why aren't search snippets considered verified evidence?
A search snippet proves only that a search backend surfaced text. It may be truncated, stale or context-free. A retrieved page gives stronger provenance, although its statements can still be false. Balanced policy permits transparent snippet support; Verified policy requires fetched evidence for citations.
How do you prevent prompt injection?
The model sees untrusted webpage text labeled as evidence. More importantly, independent code gates enforce tool names/schemas, per-run allowed fetch targets, SSRF restrictions and DLP checks. A suspicious-text detector provides signals but is not the security boundary.
What happens if the server crashes halfway through?
SQLite contains graph checkpoints and sequenced events. On restart, in-flight rows become interrupted. A capability-gated resume reconstructs runtime deadline/model configuration, resumes from the persisted boundary, and never assumes exactly-once tool execution. The interrupted node may repeat.
How does your React UI avoid duplicate runs on reconnect?
Run creation uses an idempotency key; SSE replay is read-only. Events have monotonically increasing sequence IDs persisted before publish, and the client deduplicates on replay. Two subscriptions never imply two worker instances.
What would you change for enterprise production?
Replace single-user local auth with managed identity and tenant-level authorization, use a scalable run queue/worker isolation, stronger outbound network control, encrypted/retained state policies, observability backend, controlled deployments, and real-model red-team/quality studies. Docker packaging currently lacks runtime validation.
How do you quantify correctness or ROI?
Offline evals test known behaviors; live evaluations need blinded human/ground-truth rubrics over representative questions. Productivity ROI would require time-to-answer, expert correction time, rework rate and compute cost measured before/after; do not confuse test pass counts with accuracy percentages.
Why can two Gemini models produce different timings?
Provider latency, model architecture, thinking setting, tokens emitted, search results, pages fetched and random variation all affect duration. The observed 32.1s vs 77s was a single run per model at different thinking levels, not an apples-to-apples statistically controlled benchmark.
